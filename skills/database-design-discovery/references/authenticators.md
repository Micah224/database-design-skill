# Authenticators

Assurance ceiling, phishing resistance and the schema fields each authenticator type needs. Reference: NIST SP 800-63B-4 (final, 31 July 2025); W3C WebAuthn Level 2 (Recommendation, 8 April 2021; Level 3 is a Candidate Recommendation Snapshot dated 26 May 2026); FIDO CTAP 2.3 (Proposed Standard, 26 February 2026); CISA *Implementing Phishing-Resistant MFA*.

Rules that are routinely got wrong: authenticators are **rows, not columns**; the failure counter is scoped to *a specific authenticator on an account* (limit 100 consecutive), not to the account as a whole; email **SHALL NOT** be used as an out-of-band factor; syncable passkeys **SHALL NOT** be used at AAL3; reauthentication overall timeouts are 30 days (AAL1, SHOULD), 24 hours with 1-hour idle (AAL2, SHOULD), 12 hours with 15-minute idle (AAL3, SHALL for the overall timeout).

| Authenticator | Factor(s) | Assurance ceiling | Phishing-resistant | Verifier-impersonation-resistant | Schema fields | Notes |
|---|---|---|---|---|---|---|
| Password (memorised secret) | Something you know | AAL1 alone; contributes to AAL2/AAL3 with a second factor | No | No | Argon2id or scrypt hash, algorithm and parameters, last-changed timestamp, breach-check timestamp | 15-character minimum where it is the only factor (8 when combined with another factor). No composition rules. No forced rotation except on evidence of compromise. Screen against known-breached lists (SHALL). Password managers and autofill SHALL be allowed; pasting SHOULD be permitted where autofill is unavailable. No hints, no knowledge-based questions. |
| Passkey, synced | Something you have + user verification | AAL2 maximum | Yes | Yes | credential_id (up to 1023 bytes, store as bytea), COSE public key, sign_count, transports, AAGUID, uv_initialized, backup_eligible (immutable), backup_state (mutable) | Cannot reach AAL3: syncable authenticators require the private key to be exportable, and the guidance states they SHALL NOT be used at AAL3. Providers are widely reported to return sign_count = 0 on every assertion (undocumented by the vendors) - a naive "reject unless new > stored" check then rejects those users. |
| Passkey, device-bound / FIDO2 security key | Something you have + PIN or biometric | AAL3 capable | Yes | Yes | Same credential record as above, plus attestation statement and the AAGUID you are willing to trust | The only widely deployed route to AAL3 for ordinary users - though device binding alone is not sufficient: AAL3 also requires FIPS 140 Level 1+ validation, hardware-isolated key storage and phishing resistance. In the 2022 Cloudflare incident, staff entered both password and TOTP into a phishing site and the attack still failed, because the key would not assert for the wrong origin. |
| TOTP authenticator app | Something you have (single-factor OTP device) | AAL2 with a password | No | No | Encrypted shared secret, algorithm, digits, period, drift window, last-used step (to block replay) | Phishable in real time: the user reads a code and can be induced to type it anywhere. Better than SMS because there is no carrier in the path. |
| Push approval with number matching | Something you have | AAL2 | No | No | Device registration id, push token, per-challenge nonce, displayed number, response and timestamp | Number matching is what stops MFA-fatigue bombing. Push without number matching is materially weaker and is ranked below it in the CISA hierarchy. |
| SMS or voice one-time code | Something you have (restricted authenticator) | AAL2, but classified as restricted | No | No | E.164 number, verification status, carrier-change or SIM-swap signal, per-code hash and expiry | NIST treats the public telephone network as a restricted channel. Google telemetry: SMS codes blocked 100% of automated and about 96% of bulk phishing attacks, but materially less against targeted ones. Keep as last resort; never sufficient alone for a payment or a permission change. |
| Email one-time code or magic link | Not a possession factor | Not permitted as an authentication factor | No | No | Single-use token hash, purpose, expiry, consumed-at timestamp, requesting IP | The guidance is explicit that email SHALL NOT be used for out-of-band authentication: an inbox is itself reachable with a password from anywhere. Legitimate for address verification and enrolment, not for signing in. |
| Backup codes (look-up secrets) | Something you have | AAL2 as a second factor | No | No | One hashed row per code, used_at, issued_at, remaining count | Hash them like passwords, mark them individually used, and show the user how many remain. The cheapest recovery path that does not weaken the account. |
| Smart card / PIV / CAC | Something you have + PIN | AAL3 | Yes | Yes | Certificate subject and serial, issuing CA, validity window, revocation-check timestamp | The government baseline. Requires a certificate lifecycle you must actually operate, including revocation checking on every use. |
| Social sign-in (Google, Apple, Microsoft) | Depends entirely on the provider | Inherited from the provider - you do not control it | Inherited | Inherited | Issuer, subject, unique on (issuer, subject); never on email | You inherit the provider assurance and cannot raise it. The (iss, sub) pair is the only stable key - email is mutable and can be reassigned, so joining on it eventually merges two different people. |
